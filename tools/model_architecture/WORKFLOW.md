# 模型架构图绘制规范与经验

本规范来自 Kimi-K3、DeepSeek-V4-Flash 和 Kimi-K3.1-Pro 的实际绘图、纠错和用户反馈。后续模型先按此流程审阅资料，再构造图。目标是**结构可解释、变化可追溯、图面可读、PNG 与原生 draw.io 同源**。

## 1. 分开保存事实、拓扑和版式

采用以下顺序，不用漂亮的排版掩盖不确定结构：

```
模型与版本 → 固定来源 → 参数及差异 → 审阅计算路径
          → graph JSON → 版式与连线 → 原生 draw.io → PNG → 检查与提交
```

- `sources.json` / inventory：具体公开文件、固定 revision、获取结果和哈希。
- `facts.json` / config 快照：参数值、作用域、定位与冲突，不凭记忆填数。
- `review.json` / `architecture_review.md`：结构问题、证据和未完成项。`pending` 是待核对，模板本身不证明事实。
- graph JSON / 模型构造器：节点、边、来源、状态、描述及模型专属拓扑。
- presentation 模块：位置、尺寸、短标签、字体、同名端口和简化走线；不得悄悄增删计算分支。
- `.drawio`：正式 PNG 的直接源文件；`.export.json` / `.layout.json`：配对与实测版式记录。

## 2. 来源核验：先确定“究竟是哪一版”

1. 明确目标 `owner/model`、变体（Flash/Pro/Base 等）及作为比较基线的模型；固定 HF revision 和实现提交。`main` 只用于发现，不能成为最终版本证据。
2. 读取实际 checkpoint `config.json`、模型卡、`configuration_*.py`、模型实现／推理入口，必要时读取 processor、视觉配置、报告与 kernel。
3. 没有随权重发布 forward 时，可检查模型卡推荐推理框架的对应实现；记录它是**后端实现**，不能冒充模型仓库自带源码。
4. 按 source ID 保存下载文件，不用相同 basename 混存。如 `models/kimi_k3.py` 与 `configs/kimi_k3.py` 必须有不同 ID／缓存路径，否则可能覆盖内容并记错哈希。
5. 配置类的演示默认值不能冒充 checkpoint 值。区分 text/vision 等嵌套作用域，不把同名 hidden_size 混为一个数字。
6. 下载失败、未找到源码和真正没有该模块是三种情况。失败保留记录，不猜测；不通过关闭 TLS 或绕过网络策略获取资料。

证据能力必须说清：

| 资料 | 能支持什么 | 不能单独支持什么 |
| --- | --- | --- |
| checkpoint config | 发布的维度、层数、排布、开关和精度规则 | 完整 forward 分支和运行结果 |
| 官方报告／模型卡 | 设计、公式、声明的规模与能力 | 未公开实现的每个精确算子 |
| 模型／推理源码 | 所读版本的计算、状态和后端路径 | 其他后端都相同、实际已跑通 |
| 权重索引 | 张量名称与 shard 映射、模块存在性 | 张量形状、数值与逻辑参数总量 |
| HF safetensors 元数据 | 提供方统计；可与新增矩阵量交叉比对 | 独立 tensor-header 核验，尤其量化打包后的完整逻辑参数计数 |
| 自己运行的检查／基准 | 实际执行过的范围及结果 | 没有执行过的 GPU 推理、飞书导入、吞吐或数值等价性 |

保留未核实项；不要把未公开尺寸、未知 dense FFN 层号或推测的 MTP 路径画成已确认。

## 3. 拓扑审阅：沿张量和状态走一遍

绘图前写清：输入来自哪里、每条投影／门控从哪里分叉、归一化发生在哪一侧、状态何时写入、输出如何聚合。

| 模块 | 必查问题 | 已遇到的错误 |
| --- | --- | --- |
| 混合注意力 | 哪些层用哪种注意力？层号是0还是1起算？末尾额外层是否计入主干？ | 把93层外再加一层，或把类默认7层当成实际43层 |
| KDA／递归注意力 | Q/K/V、衰减α、更新β，以及独立输出门是否分开？Conv、激活、L2Norm和状态更新位置？ | 只画QKV三路；把输出门算进五路输入 |
| MLA／DSA | Q低秩路径、KV潜变量、位置编码、输出门顺序、索引与主注意力如何关联？ | 把换成稀疏读取误画为整个MLA投影／缓存被删除 |
| 压缩／索引 | value与gate是否独立？窗口重叠、stride、APE、softmax轴、缓存和因果可见性？ | 值路径错误经过softmax；把top-k读取数误当缓存容量 |
| 具体索引器 | 输入取h还是归一化Qr？LayerNorm还是RMSNorm？是否有RoPE／Hadamard？ | 直接套用相似模型；K3.1的索引器不做RoPE／Hadamard，不能照抄DeepSeek默认路径 |
| MoE | Router选谁、权重怎么算、何处乘权重？共享专家是否绕过latent投影？ | 把共享专家放进潜空间，或把routing weight移到不等价位置 |
| 残差 | token attention与depth aggregation是否区分？pre/post/comb及转置方向？ | 用普通加法替代AttnRes或mHC的实际聚合 |
| 视觉／辅助层 | patch、时空聚合、pool、shuffle、projector与文本融合；MTP是否独立辅助路径？ | 将说明性展开框串进真实主干；把辅助层计入主干层数 |
| prefill／decode | 完整窗口何时输出？尾部状态、环形地址、偏移与无效位置？ | 部分窗口提前写出压缩条目，或者漏掉缓存旁路 |

以真实模型专属不变量验证这些关系。未变的计算边不能为了排版被删掉；说明框和同名端口不是额外网络层。

## 4. 版本差异：先比较，再人工分类

用 `model_diff.compare_configs` 找逐字段差异，再结合模型卡和实现判断拓扑；不能从 config 增删直接推断层增删。

| 主题 | 用途 | 显示约定 |
| --- | --- | --- |
| 红色 `added` | 新模块、新计算机制或替代后的新路径 | 红框、红字，新增计算边也用红色 |
| 绿色 `removed` | 不再参与当前模型的旧路径 | 独立退役对照区，不接入新推理流 |
| 黄色 `parameter_changed` | 仅尺寸、数值、精度规则或参数统计变化 | 写清旧值→新值及统计口径 |
| 中性蓝灰 | 共享模块；旧图中已知不足的补全 | 不与差异三色争用，尤其不能让未变KDA沿用绿色造成“删除”错觉 |

特别区分：

- `auto_map`／加载类名删除，不代表神经网络算子删除。
- 两版均有的Q/KV rank新查清、dense FFN层号新确认，是**旧图澄清**，不是新模型增加模块。
- 2.78T与2.8T、104.2B与104B可能只是报告取整差异，不能据此画参数增减。
- quantization ignore规则6→8是**匹配规则**变化，不是增加两个网络模块，也不能仅此断言旧权重FP4、新权重BF16。
- 只有两版 checkpoint、报告和实现支持，才标记MTP新增／删除；不要把“旧报告有1层、两版发布config都为0”误判为新版本删除。
- 新索引器参数可以用矩阵维度推导并和元数据对照，但必须保留“提供方统计／推导／独立读取”的口径区别。

## 5. 架构、训练与软硬协同分开解释

每条优化标记为：`introduced`（本版本新增）、`inherited`（沿用）、`backend_specific`（推理实现）或 `unverified`，并附证据。

- K3.1新增DSA，不表示KDA、LatentMoE、AttnRes、MXFP4/MXFP8或MLA矩阵吸收也是它首次提出。
- 主注意力最多读2048个位置，不代表索引器不扫描历史，也不代表全模型固定复杂度或512倍端到端加速。
- 参数权重位宽、激活量化、KV cache和索引cache是不同对象；不要把MXFP4专家精度套到索引Q/K上。
- 低秩缓存减少每位置数据量；稀疏选择减少主注意力读取的位置数；递归状态聚合历史；三者不要画成同一个机制。
- fused kernel、分页缓存、矩阵吸收、通信重叠和CUDA Graph标在独立实现说明中。核实后端与硬件适用范围，不把Blackwell特定内核说成所有GPU的固定执行流程。
- 后训练带来的能力改进与架构／运行时效率分开；没有实测就不写吞吐、加速比、显存峰值或推理等价结论。

## 6. 图面表达与布局

1. 默认自下而上：输入在下、输出在上，重复主干居中或作为明确主轴；相关展开模块相邻。用户指定参考图时继承其模块组织，允许为可读性调整几何。
2. 节点主要写**算子名称＋必要维度**，通常一到两行，如 `Linear Q↓ / 7168→1536`、`LayerNorm`、`Matmul`、`ReLU`、`TopK≤2048`。长解释、来源、边界与精度条件放到 tooltip／evidence／README。
3. 不把每一层说明都做成等宽大色条，也不靠缩到极小字号塞下段落。先改短标签、合理换行和尺寸，再调整字体。
4. 字体使用常见Arial；设标题、模块标题、算子、次要维度几个层级，避免17/19/21等大量近似字号混用。字号随原生画布调整，不把某模型的大画布像素值硬套到别的模型。
5. 主链对齐；分叉使用可读的并行lane；共享来源可用明确的分叉／总线；Q/K/V、控制门和缓存不要堆到同一列。
6. 简单 `+`／`×` 用小型圆节点；缓存与普通算子区分；时间窗口／状态优先用**原生张量格和简单状态图**，不要堆长文字。
7. 复杂模型拆总览与注意力／压缩器等详细页。总览画整体关系，详细页展开关键分支；不要把高密度细节和所有硬件实现同时塞进首页。
8. 跨面板使用同名张量端口时，写出名称、形状，并保存 `port_bindings`；注明它是同一张量引用，不暗示复制或新增计算。
9. 视觉检查缩略图看层级和留白，再放大看文字、公式和锚点。不能只看节点数量或“导出成功”。

### 节点尺寸必须体现算子与信息量

每个节点同时考虑算子视觉角色、名称／维度长度、分支接口及前后节点关系，不能机械等宽等高，也不能单靠名称长度替代复杂度判断。

| 视觉角色 | 建议表达 |
| --- | --- |
| 简单激活、归一化、mask | 紧凑矩形，通常一行；与前后节点中心线对齐 |
| Linear／投影 | 中等矩形，名称与维度分行；同层并行投影按行对齐 |
| Matmul／聚合／TopK | 按输入接口及表达宽度留空间，尺寸不必与ReLU相同 |
| Cache | 尺寸体现名称／形状并与读写路径对齐，避免与普通算子混淆 |
| Attention／MoE等复合模块 | 模型构造器显式判断角色，留足信息空间；必要时展开子图 |
| 加法／乘法 | 小型符号节点；不为与长算子等宽而拉伸 |

可复用 `operator_layout.fit_operators`：在构造器预留lane内按文本与视觉角色调整宽高，保持中心轴，先换行再考虑减小字号。共享张量输入／Split等分叉节点还需覆盖子分支接口跨度，不能仅按短名字收得过窄，导致本可直连的分支新增绕线。视觉角色只是排版判断，不是算法复杂度／性能证明。默认尺寸仅为起点，仍需逐图审阅，检查分叉、收敛、留白和实际文字边界。尺寸变化后重新计算端口和路线，不能沿用已经错位的折点。

### 用户认可的排版参考

用户已认可 GLM-5.1 的自适应算子框版本（提交 `f4caaa9`）。后续没有另行指定风格时，优先沿用这套**排版方法**：

- 参考图：[GLM-5.1 PNG](../../models/glm_5_1/glm_5_1_architecture.png) / [原生 draw.io](../../models/glm_5_1/glm_5_1_architecture.drawio)。以该提交可查看当时认可的版本，后续文件可能继续更新。
- 简单算子用紧凑框；Linear等投影按名称与维度分行；Matmul、聚合、缓存和复合模块分别留出合适空间，不机械统一宽高。
- 相邻串行节点对齐中心轴；并行分支按计算层级对齐；分叉节点还考虑各子分支的接口跨度，使短名字节点也能合理分发数据。
- 先调整框尺寸与换行，再考虑减小字体；保持正文可读、标题分层和节点留白，长解释移入description与证据文档。
- 调整尺寸后重新选端口、简化走线并检查实际渲染。直线优先；必要的分叉与避让不为追求折点数量而删除。
- 新模型复用此布局原则与工具函数，不复制GLM的DSA、RoPE、维度、层数或辅助模块假设，也不固定使用相同画布坐标。

推荐调用顺序：

```python
from operator_layout import fit_operators
from routing import simplify_connections

# 图中的事实、分支和预留lane先由模型审阅与构造器确定。
# roles只指定视觉角色，不用于证明算子的算法复杂度。
fit_operators(graph, roles=reviewed_visual_roles, font=20)
simplify_connections(graph)
# 然后生成原生draw.io → export-png → verify-png，并放大／缩略审阅。
```

实现参考：`operator_layout.py` 与 `examples/build_glm51.py`。此认可仅针对显示效果；来源核验、结构正确性和同源交付要求仍独立适用。

## 7. 连线：先对齐端口，再选择最短清晰路径

优先级：**单段直线 → 一个直角 → 必要避让**。

- 同列链使用相同x端口，同层使用相同y端口；不要因几像素偏差让自动路由加出两个折点。
- 共享输入的宽节点可对齐各投影列直接分叉；不要强制全部从中心出线再绕回。
- `routing.simplify_connections(graph)` 只改变端口与路线，保留source/target，并避让无关运算节点及安全留白。
- `edges[].routing: "straight"` 关闭draw.io额外自动绕线；有一个显式waypoint时绘成单直角。必须仍为对齐的正交线，不能以斜线穿过算子来减少折点。
- 跨模块、绕过中间算子或旁路回收时可保留必要折线；不要追求“全部直线”而改变运算关系。
- 统计**渲染后的** `.layout.json` 路径，而不是仅数JSON中的waypoints。K3.1实际从67折点降到20，154条连接中136条直线；这些是案例结果，不是所有模型必须满足的比例。

## 8. 交付与后续修改

完成以下检查后再交付：

- 来源固定、失败可追溯；结构与参数口径核对；未核实项明确。
- 计算边完整；层号、数量、门控、缓存、shared／routed、辅助路径有模型专属验证。
- 非背景运算节点不重叠；实际文字不溢出且有留白；连接正交且不穿无关算子。
- `.drawio` 为未压缩原生节点／边，无整图位图；PNG直接由它导出，并有同名 `.layout.json`、`.export.json`。
- `verify-png`通过。多页总图仅首页导出时，每张正式详细PNG仍有独立XML配对；总图中的详细页与独立文件保持一致。
- 不能声称“已实测飞书导入”“已GPU推理”“已核对tensor shapes”，除非确实做过。
- 修改从唯一结构源开始。若手改XML，重建前先同步JSON，避免覆盖人工修改；不单独修补正式PNG。
- 更新README和来源／限制说明；运行相关检查；按用户已有授权提交并推送指定分支。不要自行发布云环境或更改默认分支。

## 9. 从工具开始一个新模型

```bash
python tools/model_architecture/model_architecture.py init-study org/NewModel \
  --revision CHECKED_REVISION --github org/ModelRepository \
  --out /workspace/new-model-study

# 可选：同时建立比较基线
python tools/model_architecture/model_architecture.py init-study org/NewModel \
  --revision NEW_REVISION --baseline org/OldModel \
  --baseline-revision OLD_REVISION --out /workspace/model-diff-study
```

命令只生成资料清单与待审阅模板，不联网、不执行模型、不猜网络拓扑，也不覆盖已有文件。填写审阅记录后，继续使用README中的 `collect → extract → draft → validate/render → export-png → verify-png` 命令。

现有可复用组件：

| 组件 | 复用内容 | 不应硬套的部分 |
| --- | --- | --- |
| `model_architecture.py` | 收集、提取、验证、原生导出入口 | 任意模型的forward语义 |
| `model_diff.py` | 字段比较、红绿黄主题 | 从字段变动自动猜层增删 |
| `routing.py` | 安全直连、单折点和保留必要避让 | 为减少折点删除分支 |
| `png_export.py` | mxGraph实测布局、配对哈希 | 语义、数值等价或飞书实测 |
| `examples/build_kimi_k31_pro.py` | 基线继承、模型差异证据与构造方式 | Kimi专属维度和DSA公式直接套到新模型 |
| `examples/kimi_k31_presentation.py` | 字体层级、短标签、主链对齐 | 固定坐标照搬到不同密度的图 |
| DeepSeek构造器及展示层 | 总览／详细页、压缩与状态展开 | 默认假定所有DSA都带RoPE／Hadamard或压缩cache |

### 用户确认的维度标注方式

需要输入输出维度时，将关键形状直接写在对应计算连线旁（原生edge label），不要改为单独的维度说明区。算子框保留简短名称／必要参数，连线展示张量如何改变；对reshape、head拆分、缓存序列T和查询序列S分别核对。根据标签长度增加行距或调整偏移，检查标签不压节点、不相互重叠。只在文档解释替代实现视图，不将另一种布局的维度混入当前计算路径。
